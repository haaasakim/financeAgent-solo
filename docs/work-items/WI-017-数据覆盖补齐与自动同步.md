## 1. 背景

2026-11-04 的数据体检发现：

| 指标 | 实测 |
|---|---|
| 标的字典 | 7,224（股票 5,561 / ETF 1,659 / 指数 4） |
| 有日K的标的 | 7,220，但其中仅 3,162 只有 250 根以上 |
| 2018-01-02 ~ 2024-01-01 有日K的标的 | 2,924（深市 2,922 + 沪市 2 个指数） |
| 沪市有日K的标的 | 3,243 只，其中 3,241 只不足 30 根 |
| 北交所有日K的标的 | 343 只，全部只有 1 根 |
| 估值表无对应日K的行 | 4,559,745 |

根因是 `--sync.missing` 只识别「零行」标的（`NOT EXISTS daily_bar`）。全量初始化中断后，
增量同步给沪市标的写入了最近几天数据，于是这些标的永远不再被补历史；同时首页的
「已覆盖标的」按「有过任意一行」计算，显示约 99.9% 覆盖，掩盖了历史缺口。

WI-016 的全部回测因此只覆盖深市，结论中的“全市场”不成立。本工作项先补齐数据，
再把每日同步从「人工记得跑」改为应用内自动调度。

## 2. 目标与范围

**目标**：

1. 增加覆盖审计：按「首尾是否覆盖完整历史区间」识别历史缺口，而不是只看零行或根数比例。
2. 增加缺口回填：对缺口标的整段重拉，幂等 upsert，不删除既有数据，可重复执行。
3. 增加每日同步编排与收盘后调度：应用运行时自动执行，不依赖人工记忆。
4. 补齐沪市/北交所历史日K后重算因子，并保留回填前后的可核对结果。

**范围内**：

- `--sync.audit`、`--sync.backfill=N`、`--sync.daily` 三个命令行入口
- `DailySyncService` 编排：字典 → 日K增量 → 因子增量 → 估值增量 → 市场快照
- `DailySyncScheduler`：交易日 16:10、启动补同步、并发保护
- 覆盖审计/回填/编排/调度的单元测试
- 本次历史回填的执行与结果记录

**范围外**：

- 退市股补数、分钟级行情
- 新增第二个日K Provider（腾讯 501 的容灾）——列为后续工作
- 外部 launchd/cron 脚本（应用内调度已覆盖；应用不运行时仍需外部拉起）
- 重跑 WI-016 全量策略搜索（本次先完成数据补齐）

## 3. 契约

### 3.1 命令行

| 参数 | 行为 | 写库 | 外部请求 |
|---|---|---|---|
| `--sync.audit` | 打印覆盖审计摘要与缺口样例 | 否 | 否 |
| `--sync.backfill=N` | 回填缺口标的；N 为本轮上限，0 表示不限 | 是（upsert） | 是 |
| `--sync.daily` | 执行一次完整每日同步 | 是 | 是 |

### 3.2 覆盖判定

- 应有交易日：全库出现过的交易日中，落在
  `[max(上市日, 最新交易日 - history-years), 最新交易日]` 内的日期数。
- 上市日缺失（历史同步从未成功）时从历史起点算；首次回填补齐后由
  `updateListedAt` 回填为实际首根日K，下一次审计不再误判。
- **充分**：首根不晚于应有起点 + `coverage-start-grace-days`，且末根不早于最新交易日
  - `coverage-stale-days`；区间内部空洞视为停牌，不判缺口。
- **缺口（回填目标）**：零行，或首根晚于应有起点超过宽限。
- **近期无成交（不回填）**：首根正常、末根早于最新交易日超过宽限，通常是停牌/退市整理，
  反复重拉也无法补出数据，单独列出供人工判断。
- 这样 000007.SZ 这类长期停牌股不会因为根数比例低被无限重拉，沪市“只有最近 20 根”
  仍会被稳定识别；000016.SZ 等停牌股也不会被误当作可回填缺口。

### 3.3 调度

| 配置 | 默认 | 说明 |
|---|---|---|
| `finance.sync.schedule.enabled` | `true` | 关闭后不创建调度 Bean |
| `finance.sync.schedule.cron` | `0 10 16 * * MON-FRI` | 收盘后执行 |
| `finance.sync.schedule.zone` | `Asia/Shanghai` | 时区 |
| `finance.sync.schedule.catch-up` | `true` | 收盘后启动且当天未同步时异步补一次 |
| `finance.sync.schedule.watchdog-enabled` | `true` | 墙钟看门狗，解决 macOS 睡眠漏跑 cron |
| `finance.sync.schedule.watchdog-ms` | `60000` | 看门狗检查间隔 |
| `finance.sync.schedule.watchdog-retry-minutes` | `15` | 补同步失败后的重试节流 |
| `finance.sync.daily-lock-path` | `data/.daily-sync.lock` | 跨进程互斥锁文件 |

- 交易日判定：拉取基准 `000300.SH` 最近 10 天日K，若包含今天才执行；休市或数据未更新则跳过。
- 并发保护：同一 JVM 内 `AtomicBoolean`；跨进程用 `data/.daily-sync.lock`（FileLock），
  8080/8081 同时运行或定时任务与手动 `--sync.daily` 重叠时只允许一个进程写库。
- 失败策略：日K `FAILED` 时跳过因子/估值，但仍同步快照；所有步骤结果写入
  `sync_log` 的 `DAILY_SYNC` 记录。
- 测试环境通过 surefire 系统属性关闭调度，避免 16:10 后跑测试误触发外部请求；
  `DailySyncServiceTest` 使用独立的锁文件，避免与运行中的真实同步互斥。

## 4. 数据安全与回滚

- 回填只做 upsert，不删除既有行；拉取失败时旧数据保持原样。
- 回填前已做整库备份：`data/finance.db.bak-pre-backfill-20261105`（约 5.4 GB，gitignore）。
- 回滚：停止进程，用备份文件覆盖 `data/finance.db`（同时删除 `-wal`/`-shm`）。
- 回填任务记录在 `sync_log`，任务名 `BACKFILL_DAILY_BARS`；每日编排记录 `DAILY_SYNC`。
- 不修改表结构，不新增迁移。

### 5.5 2026-11-05 16:10 漏跑复盘

- **现象**：21:23 数据仍停在 2026-11-04；`fa-8081.log` 没有任何 16:10 调度日志，
  但进程一直存活。
- **日志证据**：白天持续出现 `HikariPool - Thread starvation or clock leap detected`，
  间隔约 17~20 分钟，说明机器反复休眠。Spring 的 cron 基于单调时钟，睡过 16:10
  不会补跑；这是本次“没更新”的直接原因，不是数据源或 Bean 装配问题。
- **处置**（`3448b4d`）：增加墙钟看门狗，每 60 秒检查一次；已过 16:10、当天是交易日、
  最新截面不足 90% 或最新日期落后时补同步；失败按 15 分钟节流；与手动同步共用
  `data/.daily-sync.lock`。
- **实测**：
  - 21:24:41 本机 8080 实例重启，启动补同步触发；
  - 21:26:38 8081 看门狗也触发，但被文件锁挡住并记录跳过（跨进程互斥生效）；
  - 22:26:44 同步完成，`DAILY_SYNC` SUCCESS 5/5；
  - 2026-11-05 日K与因子均为 7,292 只。
- **结论**：cron 负责准点，看门狗负责兜底。只要进程存活，收盘后任意时刻唤醒，
  最迟一个检查周期（60 秒）内会补当天的数据。

## 6. 未验证项与剩余风险

- 行情源已改为「东财主 + 腾讯备」：东财一次请求取 10 年，腾讯仍可能被 WAF 拦截；
  两源 qfq 小数位不同（东财 2 位、腾讯 3 位），首次切源会触发一次全量重拉归一化。
  `daily_bar.source` 会混合 `EASTMONEY_KLINE` / `TENCENT_FQKLINE`，需按 source 追溯。
- 512390.SH 两源均无数据，暂不修复；需人工确认代码是否已退市/改名。
- 应用不运行时调度不会执行；当前依赖应用常驻（本机 8080/8081 已常驻）。
  如需“应用没开也能补”，需要 launchd/cron 外部拉起，属后续工作。
- 16:10 cron 在 macOS 睡眠下不可靠，实际由看门狗兜底；若整晚不休眠且应用未运行，
  或收盘后一直未唤醒，则当天不会更新，次日增量会补。彻底解决仍需外部调度器。
- 交易日探测在数据源延迟时会跳过当天，看门狗每 10 分钟重探，通常当天可补上。
- 回填后因子需全量重算（`--factor.init`），本次在数据补齐后执行。
- 本次不回填退市股；幸存者偏差仍在。
- WI-016 的策略结论需在补齐沪市后重跑，不能直接沿用。
